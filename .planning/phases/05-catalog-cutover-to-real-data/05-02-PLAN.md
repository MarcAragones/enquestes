<objective>
Prove the catalog and the explorer actually behave correctly now that several real surveys are live at once, and close the one structural path by which one survey's data could bleed into another's page.

Purpose: PUB-04. v1.0's homepage grid and explorer were built and verified against a single dataset. Three real surveys are now published with materially different shapes — 283, 291 and 263 fields, 6, 1 and 4 KPIs, 2000, 6706 and 2000 respondents — and "it worked with one" is not evidence for "it works with several".

Output: a regression suite grounded in the real published data (not synthetic fixtures) covering cross-survey `?chart=` behaviour and per-survey field-set divergence, a render-time guard in `ExplorerPage` that makes the no-bleed guarantee structural instead of accidental, an index-driven completeness gate in `verify-pages.mjs`, and a recorded human walkthrough of all five phase success criteria.
</objective>

<flagged_assumptions>
The deterministic edge probe returned `unclassified`/`unresolved` for PUB-04, so its edges were derived by hand here and are recorded rather than assumed:

- **A-04 (SC-3, reachability of the bleed):** with today's navigation graph, `ExplorerPage` always unmounts between two surveys, so the stale-state bleed is **currently unreachable**. Task 2 is therefore hardening, not a bug fix, and must be described as such in the summary. It is still worth doing because the guarantee is presently an accident of the link structure — one future in-app "next survey" link or programmatic `navigate()` between two `/enquesta/:id` routes would silently turn it into a live defect, and the sibling component already carries the guard.
- **A-05 (SC-2, "with suppression applied where the sample is too small"):** no real survey can trigger suppression — every published KPI's effective n is 2000 or 6706 against a `MIN_KPI_SAMPLE` of 10. This criterion is therefore verified as *the rule is intact and correctly withholds nothing*, proven by exercising the predicate on both sides of the threshold in Task 1, rather than by observing a suppressed KPI on the live site. Recording this explicitly so it is not later read as an untested criterion.
- **A-06 (SC-4, rejection is field-based, not id-based):** `decodeShareLink` compares shelf fids against the loaded survey's field names. Because REO1167 and REO1145 share 196 field names, a chart whose shelves use only shared fields **will legitimately render on both** — that is correct behaviour (the fields exist, the chart is meaningful), not a cross-survey leak. The genuine cross-survey rejection case is a chart using a field one survey has and another does not. Task 1 tests both directions so this nuance is documented in code rather than discovered later as a surprise.
</flagged_assumptions>

| `?chart=` query param → GraphicWalker `chart` prop | Fully visitor/attacker-controlled input reaching a rendering library, with no server to validate it. |
| URL `:id` segment → data fetch + field allow-list | The route param selects both which data is fetched and which field list a share link is validated against; a mismatch between the two is the cross-survey bleed. |
| `public/data/*.json` → React render tree | Static JSON fetched at runtime and rendered; `parseEnquestesIndex` / `parseEnquestaMeta` are the two trust boundaries that reject malformed payloads. |
