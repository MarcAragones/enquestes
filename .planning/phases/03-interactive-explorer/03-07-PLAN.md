<objective>
Close gap G-03-5 (blocker): the survey summary modal still opens and then closes
immediately under `npm run dev`, even after plan 03-04 (commit 90ca09d) shipped a
fix for this exact symptom (originally G-03-2).

Root cause, fully diagnosed in `.planning/debug/g-03-5-modal-still-closes.md`
(status: diagnosed, hypothesis CONFIRMED): the WHATWG HTML spec's `close()`
algorithm does not dispatch the native `close` event synchronously — it queues it
as a separate browser task ("queue an element task on the user interaction task
source... to fire an event named close"). React StrictMode's dev-only mount
double-invoke (setup -> cleanup -> setup) runs entirely synchronously within one
effect-flush pass, well before that queued task can run. So:

  1. Setup #1 attaches handlerA and opens the dialog.
  2. StrictMode's synchronous simulated-unmount cleanup detaches handlerA and
     calls `close()` — which closes the element but only QUEUES the close event.
  3. StrictMode's synchronous remount setup #2 attaches a NEW handlerB (wired to
     the real `onClose`) and reopens the dialog.
  4. Later, the event queued in step 2 finally fires — and handlerB, attached in
     step 3, receives it. It invokes the real `onClose`, deleting the
     `?enquesta=` param that is the sole thing keeping the modal mounted
     (`HomePage.tsx:88`). The modal vanishes.

03-04's fix ordered its cleanup as detach-listener-then-close, which defends only
against a SYNCHRONOUS dispatch into the OLD listener. That defence is void here:
the dispatch is asynchronous and lands in a NEW listener re-attached in the
interim. Do not repeat that approach.

This is the SECOND fix attempt for this symptom. The first one passed lint,
typecheck, build and code review and still did not work, because every one of
those gates is blind to event-loop timing. Therefore this plan does not merely
change the component — it first builds an automated reproduction of the failure,
proves that reproduction fails against 03-04's implementation, and only then
applies the fix.

Purpose: restore HOME-03 (see the quick KPI summary) and HOME-04 (reach the
explorer from that summary), both unreachable while the modal self-dismisses.
Output: a framework-free `openDialogLifecycle` function with a regression test
that reproduces the StrictMode/async-close race, and `SurveySummaryModal.tsx`
rewired to use it.

Chosen approach — option (a) from the diagnosis, a suppression counter, in
preference to option (b) (never closing in cleanup):

- It is timing-agnostic. It behaves correctly whether the browser dispatches the
  close event synchronously, on a microtask, or on a macrotask. Both previous
  attempts at this bug died on an assumption about that timing, and the debug
  session explicitly records the exact scheduling primitive as an unresolved
  blind spot. A fix whose correctness does not depend on that unknown is the
  right answer here.
- It keeps an explicit `close()` on a genuine unmount-while-open — the path taken
  by the "Explorar dades interactives" button, which unmounts the modal while the
  dialog is still open. Option (b) would delegate top-layer teardown entirely to
  the browser's dialog removing steps; that is specified behaviour, but leaving
  an explicit close in place avoids betting the explorer page's interactivity on
  it across browsers.

    STEP 2 (GREEN). Now write the real implementation in
    `src/lib/dialogLifecycle.ts`.

    `DialogLike` is a structural interface with an `open` boolean, `showModal()`,
    `close()`, and add/remove listener methods narrowed to the `close` event type
    with a zero-argument listener. A real `HTMLDialogElement` satisfies it
    structurally, so no cast is needed at the call site; keep it that way.

    `openDialogLifecycle` takes the dialog, a dismissal callback, and a mutable
    counter box shaped as an object with a numeric `current` property (so a React
    ref object can be passed straight in). It returns a cleanup function.

    Setup defines a close handler that reads the counter first: when the counter
    is above zero, it decrements it by one and returns WITHOUT invoking the
    dismissal callback; otherwise it invokes the callback. It attaches that
    handler, then opens the dialog only when the element reports itself closed.

    Cleanup does two things in this exact order, and the order carries the whole
    fix: FIRST, when the element is still open, increment the counter and then
    close the element; SECOND, detach the handler. Incrementing before the close
    call and detaching after it is what makes the design correct under BOTH
    dispatch timings. Under a synchronous dispatch the still-attached handler
    consumes the count immediately; under a queued dispatch the handler attached
    by the next setup consumes it later. Either way exactly one close event is
    absorbed per lifecycle-initiated close, and the counter returns to zero.

    Guarding the increment and the close on the element being open matters too:
    it means a cleanup that follows a genuine dismissal (element already closed)
    neither closes again nor leaves a phantom count behind that would eat the
    visitor's next real dismissal.

    Write a comment above the cleanup explaining, in the same explanatory
    register the surrounding project code already uses, why the close event
    cannot be assumed to arrive during the close call, and why counting absorbed
    closes is what makes this independent of that timing. Cite the gap id so the
    next reader knows this code has a history.

    fails, so it must survive the fix untouched.

    here in this task.
