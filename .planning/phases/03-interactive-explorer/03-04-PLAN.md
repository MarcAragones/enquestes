<objective>
Close gap G-03-2 (blocker): the survey summary modal opens and then closes
immediately when the app runs under `npm run dev`.

Root cause (fully diagnosed in `.planning/debug/g-03-2-modal-closes-immediately.md`,
status: diagnosed, hypothesis CONFIRMED): `SurveySummaryModal.tsx` splits the
native `<dialog>` lifecycle across two independent effects that are not
idempotent under React StrictMode's dev-only mount -> simulated-unmount ->
remount cycle. Effect 1 (lines 25-29) unconditionally calls `dialog.close()` in
its cleanup; Effect 2 (lines 31-37) has a `close` event listener still attached
at that moment which invokes the `onClose` prop. `onClose` is HomePage's
`onCloseSummary`, which deletes the `?enquesta=` search param — the only thing
keeping the modal mounted (`HomePage.tsx:88`). So React's *simulated* unmount
produces a *real*, persistent state change and the modal disappears.

This is a pre-existing Phase 1 defect (both files untouched since commit
c8e3d8a), masked because Phase 1's verification ran against a production
preview build where StrictMode's double-invoke never runs.

Purpose: restore HOME-03 (see the quick KPI summary) and HOME-04 (reach the
explorer from that summary), which are both unreachable while the modal
self-dismisses.
Output: one merged, idempotent dialog lifecycle effect in
`src/components/SurveySummaryModal.tsx`, plus a human confirmation under the
dev server — the exact condition that exposed the bug.

Known coverage limit (recorded, not silently omitted): this repo has no DOM
test environment — `vite.config.ts` sets `test.environment: 'node'` and no
jsdom/@testing-library packages are installed, so no automated component test
can drive a real `<dialog>` through a StrictMode remount. Adding that harness
means three new dev dependencies and a package-legitimacy checkpoint, which is
out of scope for this gap-closure pass; it is left as a deferred follow-up. The
automated gates below are regression gates (lint + typecheck + existing suite);
the behavioural gate is the task's `<human-check>`, which the verifier harvests
at end of phase.
</objective>

  <name>Task 1: Merge the dialog lifecycle into one StrictMode-idempotent effect</name>
  <files>src/components/SurveySummaryModal.tsx</files>
  <read_first>
    src/components/SurveySummaryModal.tsx — the two effects at lines 25-29 and
    31-37 are the whole defect surface; everything below line 39 (the id guard,
    the meta fetch effect, the backdrop handler, and the entire JSX body) stays
    untouched.

    src/pages/HomePage.tsx — lines 67-72 and line 88 show why a spurious
    `onClose` is destructive rather than cosmetic: `onCloseSummary` deletes the
    `?enquesta=` param and line 88 gates the modal's very existence on that
    param. Also note `onCloseSummary` is re-created on every HomePage render,
    which is why the merged effect must not take `onClose` as a dependency.
  </read_first>
  <action>
    Replace the two separate effects (the `[]`-dependency show/close effect and
    the `[onClose]`-dependency close-listener effect) with a latest-value ref
    plus one single lifecycle effect that owns both the listener and the
    imperative open/close.

    Add a ref holding the newest `onClose` callback, refreshed on every render
    by a dependency-less effect that assigns the prop into the ref. This is the
    standard latest-ref pattern and it exists here for a specific reason: the
    caller re-creates `onCloseSummary` on every render, so keeping `onClose` in
    the lifecycle effect's dependency array would tear down and rebuild the
    dialog lifecycle on every parent render.

    Then write the single lifecycle effect with an empty dependency array. Its
    setup reads `dialogRef.current`, returns early when the ref is null,
    defines a close handler that invokes the callback held in the ref, attaches
    that handler as a `close` event listener, and only then calls `showModal()`
    — guarded on the element's `open` property being false so a repeated setup
    can never raise `InvalidStateError`.

    Its cleanup must detach the `close` listener BEFORE calling `close()` on the
    element. That ordering is the entire fix: with the listener already
    detached, the imperative close performed during React's simulated unmount
    dispatches its native event into nothing, so the parent's param-deleting
    callback is never invoked for a lifecycle event that was not a visitor
    action. Calling `close()` on an element that is already closed is a
    specified no-op that dispatches no event, so a genuine dismissal followed by
    a real unmount stays correct too.

    Trace the four paths before you finish and satisfy yourself each one holds:
    StrictMode's simulated unmount (listener detached first, so no callback);
    the remount right after (element is closed, so the `open` guard permits
    `showModal()` again); a genuine dismissal via Escape / the Tanca button /
    a backdrop click (listener is attached, so the callback fires exactly once);
    and a real unmount after that dismissal (element already closed, so the
    cleanup's `close()` is a no-op).

    Do not change the fetch effect, `handleBackdropClick`, `handleExplore`, or
    any JSX. Do not change `HomePage.tsx` — memoising `onCloseSummary` there
    would paper over the symptom while leaving the non-idempotent cleanup in
    place, and the diagnosed cause is in the modal's effect structure.

    Keep the file's existing comment voice: explain WHY the cleanup order
    matters, in the same explanatory register the surrounding comments already
    use.
