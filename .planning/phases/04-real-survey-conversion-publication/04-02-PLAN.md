<objective>
Run each of the operator's 2-5 real survey exports through the pipeline, fix reactively whatever real-world format gaps they surface, and get an explicit operator decision on every privacy finding — all before anything is written to `public/data/`.

Purpose: this is the phase's operational core. The exports exist only on the operator's machine, so nothing here can be planned speculatively: the format gaps are discovered by running the pipeline, and the privacy findings are resolved by the person who knows what the columns mean. The milestone-level decision already made is "just run it and fix what breaks", with the same regression discipline the v1.0 semicolon-delimiter gap G-02-3 established.

Output: every real export loads and reaches the privacy checklist; each format fix has a regression test; each survey has an approved column set and a recorded privacy resolution ready for publication in plan 04-03.

Scope boundary: this plan writes nothing to `public/data/` and touches nothing in the React app. Publication is 04-03; retiring `mostra-sintetica` is Phase 5.
</objective>

Each survey's checklist has now been run and printed. I will present them one survey at a time, with the full report text and, for each finding, what it actually means for that survey.

Three kinds of finding can appear:

- `near-unique` — a column with more distinct values than the uniqueness ratio threshold of 0.9 allows. Almost every respondent has their own value, so the column is close to an identifier on its own.
- `quasi-identifier-name` — the column's name matches a known re-identification hint (age, birth date, postal code, department, job title, municipality, gender). This fires regardless of the column's cardinality, which is how a low-cardinality postal-code column gets caught.
- `small-group` — a combination of two or three dimension columns produces at least one group with fewer than 5 respondents. Anyone who knows one person in that group can read that person's answers off the chart.

The report also lists columns it could not evaluate. Those are not passes.

Why this stops here rather than being decided for you: the converter blocks with exit code 2 until `--confirm-privacy-review` is passed, and that gate exists so a person reads the report. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator's real export file → `load_table` | The file is produced by a third-party survey tool. Its structure is not controlled by this project and may be ragged, mis-encoded, or shifted. It is not attacker-supplied, but it is untrusted as to shape. |
| real respondent data → scratch directory → `public/data/` | This plan deliberately stops at the scratch directory. Crossing into `public/data/` is permanent and public and is gated on the Task 3 decision. |
| privacy checklist report → operator decision → `--confirm-privacy-review` | The gate that decides what becomes permanently public. Its integrity depends on a human actually reading the report. |
| reproduction files for regression tests → `scripts/fixtures/` → public git history | A regression test built from a real export would commit real respondent data. |

Explicitly out of scope, stated so the narrowness is deliberate: no authentication, no identity and therefore no Spoofing surface; no database and therefore no injection surface; no network-facing service and therefore no denial-of-service surface. This is an operator-run local CLI over the operator's own files.
